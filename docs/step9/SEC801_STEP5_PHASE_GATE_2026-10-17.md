# SEC-801 Step 5-A / 5-B gate — OFFLINE ONLY

**Version candidate:** `0.9.0a7` | **SEC-801, SEC-802 and SEC-803: OPEN**

The existing Ansible `step5-kubeadm-calico.yml` is still an isolated LAB-ONLY
playbook and MUST NOT be run on an existing host. This change introduces **no
user-facing, internal, or automatic Step5 mutating adapter**. It does not
split the dangerous Ansible playbook itself into transactional stages.

## Proposed phase boundary

1. **Step5-A (`kubeadm`)**: plan-bound control-plane identity, Ubuntu/kubeadm
   config digest, CRI/runtime prerequisites, no kubeadm/Calico footprint.
2. **Step5-B (`calico`)**: *independently attested* successful Step5-A completion
   and healthy API, clean/owned Calico resource inventory, CRDs/operator/CR
   pinned by their independently verified publisher provenance.
3. **Validation**: CoreDNS, node readiness, CNI networking and policy tests.

An operator-supplied snapshot, plan SHA or matching local file digest is NOT
proof of ownership, successful Step4, Step5-A, API health or trusted artifacts.
Even `phaseCandidateFromSnapshot=true` means **diagnostic candidate only**.
Every report sets `status=BLOCKED`, `applyAuthorized=false`,
`executionPerformed=false`, `remoteCommandsExecuted=0`,
`automaticRetryAllowed=false` and `resetAuthorized=false`.

## CLI commands (safe / no host changes)

Generate a read-only plan using the existing `kauto plan` process. To inspect a
Step5 candidate, prepare a JSON SHA-256 manifest with exactly these four keys
and *independently verified* hashes (lowercase 64-char hex strings):
`kubeadm-init.yaml`, `calico-installation.yaml`, `calico-crds.yaml`,
`calico-operator.yaml`. Their four local files must be in an artifact directory.
A `SHA256SUMS.json` generated by Kauto itself does not prove provenance.

```bash
python -m kauto step5-phase-review \
  --plan /absolute/path/plan.json \
  --cluster examples/cluster.yaml --inventory examples/inventory.yaml \
  --node-id cp-01 --phase kubeadm \
  --snapshot examples/partial-recovery-snapshot.example.json \
  --artifact-dir /absolute/path/four-artifacts \
  --sha256-manifest /absolute/path/sha256-map.json \
  --kubernetes-version 1.37.1 --calico-version 3.33.0 \
  --kube-apt-version '<EXACT_KUBE_APT_VERSION>' \
  --ack-plan-fingerprint '<64_CHARACTER_PLAN_SHA256>'
# Exit 3: intentional BLOCKED, not a failed installation.
```

For an optional phase-order simulation (always no-op):

```bash
python -m kauto step5-phase-rehearsal \
  --plan /absolute/path/plan.json \
  --cluster examples/cluster.yaml --inventory examples/inventory.yaml \
  --ack-plan-fingerprint '<64_CHARACTER_PLAN_SHA256>' \
  --fail-at kubeadm
# Exit 3: simulation only.
```

## Limitations and outstanding safety gates

- No independent cryptographically authenticated operator authorization,
  artifact signature/provenance verification, ownership attestation or
  accepted disposable-VM Step4/Step5 receipts.
- Offline snapshots can be stale or forged; no real-time authenticated probe,
  CRI handshake, API health check or exhaustive Calico object inventory here.
- YAML checks only recognize the Step5 renderer's limited shape, not kubeadm
  admission, Calico version authenticity or complete upstream manifest validity.
- Existing Step5 playbook is still a combined potentially mutating operation;
  no safely retryable/transactional kubeadm/Calico execution or rollback exists.
- No clean Ubuntu VM install or interruption/NetworkPolicy acceptance has run.

**Do not merge umbrella PR #1 into `main`, publish an installer release or run
Step5 mutating playbooks on existing VMs until independent reviews and complete
throwaway-lab acceptance pass.**
