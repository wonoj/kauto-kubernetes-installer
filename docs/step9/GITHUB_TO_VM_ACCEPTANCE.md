# GitHub release -> fresh clone -> disposable Ubuntu VM -> second release

## 0. Stop conditions and boundary

This document is an execution plan, not test evidence. **Do not execute mutating Step4/5/7 lab Ansible on VMs yet.** SEC-801 (authenticated `apply`), SEC-802 (Calico partial-failure idempotency), SEC-804 (Ansible syntax), exact pins/artifact supply-chain approvals need closure and review first. Live test evidence cannot be generated by the current offline runner.

Never test on production, lab shared with others, or nodes containing data. VM snapshots, out-of-band console, VLAN isolation, known SSH host keys and known-good restore must be available. Do not blindly disable firewall or SELinux; avoid shared CIDR.

## 1. GitHub initial publication (source-only pre-release)

Prepare a **new dedicated** public repo; do not overwrite an unrelated `k8s` repo. In repository root:

```bash
# Once GitHub repository exists and maintainer authenticates using gh auth login:
git init -b main
git add .
git commit -m 'Kauto experimental source pre-release (no safe apply)'
git remote add origin git@github.com:OWNER/kauto-kubernetes-installer.git
git push -u origin main
git tag -a v0.9.0-alpha.0 -m 'Source pre-release: no verified install support'
git push origin v0.9.0-alpha.0
# GitHub Release is explicitly labelled pre-release, not latest stable:
gh release create v0.9.0-alpha.0 --verify-tag --prerelease --latest=false --title 'Kauto source preview v0.9.0-alpha.0' --notes-file docs/step9/FIRST_RELEASE_NOTES.md
```

Never use `--latest` nor claim stable on the first release. Verify GitHub Actions and repository branch protection. No GitHub credentials should be stored in this source tree.

## 2. Fresh trusted download for tests

On a **separate test controller** (not a disposable Kubernetes node):

```bash
git clone https://github.com/OWNER/kauto-kubernetes-installer.git
cd kauto-kubernetes-installer
git fetch --tags --force
git checkout --detach v0.9.0-alpha.0
python3 tools/verify_checkout.py --tag v0.9.0-alpha.0   --origin https://github.com/OWNER/kauto-kubernetes-installer.git
python3 -m venv .venv && . .venv/bin/activate
python -m pip install -e .
python -m pip install pytest==9.0.2 ansible-core==2.18.10
python -m pytest -q
python tools/step8_gate.py --output /tmp/kauto-step8-evidence-unique.json
```

The Step8 gate **must still say BLOCKED** until evidence-backed VM checks exist. Use a separate trusted method to check the expected commit SHA via the authenticated GitHub UI or signed/attested release; comparing to the remote alone doesn't establish publisher identity.

`verify_checkout.py` validates tag, local commit, clean checkout and repository URL, **not** publisher authenticity.

## 3. Ubuntu VM matrix (after P0 remediation only)

On isolated 22.04 and 24.04 LTS disposable guest VMs, capture snapshotted baselines and genuine signed-off test evidence:

- Test A: 22.04 single-node installation from **the exact checked out tag/commit**.
- Test B: 24.04 single-node installation from the same commit and a tested OS-specific package lock.
- Test C: 1 control plane + 2 workers, fail a Join midway, ensure token revocation and safe retry.
- Test D: repeated installation and reboot; diff service/network/Swap/iptables before/after; protect unrelated resources.
- Test E: Pod-to-Pod same/cross node, ClusterIP, DNS, Calico NetworkPolicy deny and allow under a dedicated namespace; record outputs.
- Test F: Worker/node failure and read-only recovery verification; controlled destroy only after explicitly approved ownership policy exists.

Pass every required preflight and record SHA256, version pins, test script hashes, exact commit, timestamps, reviewer and FAIL/SKIP not only PASS. **No successful smoke test implies a globally SUPPORTED version.** Only add tested exact combinations to docs/COMPATIBILITY.md.

## 4. Second GitHub release (after verified success)

Address all release-blocking findings on new commits. Re-clone the final candidate tag, rerun acceptance on the **same final commit**, and obtain human reviewer approval. Publish **another immutable release**, never edit or retag the first:

- If more real-world hardening remains: `v0.9.0-beta.1` (second pre-release).
- If every required stable acceptance condition is met: `v1.0.0` (first stable release; this may be the second GitHub release chronologically).
- Reserve `v2.0.0` for subsequent incompatible public API changes per SemVer, not merely the second release.

Sign/attest release assets via trusted CI when configured; release output checksums alone are not signatures. Do not publish new versions by rerunning an old tagged build against changed source.
